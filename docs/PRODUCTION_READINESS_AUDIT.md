# Production Readiness Audit

Written on branch `feature/rider-dispatch-kitchen-delivery-menus` (merged to `main` through PR #26) on 2026-10-10 and kept up to date on `claude/epic-johnson-r4eep6` (PR #38); the follow-up work is listed in the second addendum at the end. Scope: the whole repository (web app, API, database, jobs, integrations, CI, containers), the local stack and a production build under load, and the Google Play / App Store requirements. Method: thirteen independent read-and-reproduce audit lenses over the unmodified tree (authentication, authorization, validation and injection, money flows, delivery and navigation, database performance, capacity under load, web app, backend code health, DevOps, third-party integrations, privacy and personal data, mobile and store readiness), every finding re-checked by hand before it was fixed, every fix exercised against the running API, a fresh database and the browser. Every finding in Deliverable 3 marked Fixed or Partly fixed was reproduced by hand on the unfixed tree and re-run on the fixed one; the workflow's independent three-judge pass over the lens findings finished after the first version of this report, and its outcome is recorded in the first addendum at the end.

Numbers in this report: 140 findings (18 high, 64 medium, 58 low; no critical), of which **106 fixed, 15 partly fixed, 19 open** (the report first closed with 80, 22 and 38; the follow-up work in the second addendum moved the rest). By launch priority: P0 13 (open or partly: 2), P1 52 (open or partly: 13), P2 75 (open or partly: 19).

## Deliverable 1: Executive summary

**Overall state.** The platform is a complete, working marketplace: ordering, kitchen acceptance, community-based rider dispatch, delivery with a customer PIN, online and cash payments, wallets, ledgers and payouts, staff roles, Urdu and English, live updates over sockets. The money paths are transaction-safe and were verified on a fresh database with 361 scripted checks. Before this audit it had a set of real defects that would have shown up in the first weeks of traffic: a stolen access token could take an account over for good, riders kept customers' addresses and bank details after a job, promo limits could be bypassed by racing checkouts, a client could re-price its own delivery, a refund dismissal flipped paid orders to failed, a kitchen's malformed opening hours took the public listing down, every customer behind one mobile-network address shared ten logins per quarter hour, and the rider's navigation link used a parameter Google does not document. All of those are fixed on this branch and covered by tests.

**What is left before launch.** Every code-level P0 finding is fixed; one of them (SEC-2) keeps a P1 follow-up for refresh-token rotation, and the one open P0 (MOBILE-5) is configuration: the legal pages show a draft banner until the company identity build arguments are set and a lawyer has signed the texts off. The open P1 items are decisions and infrastructure rather than bugs: a refresh-token table for per-device sign-out, the staff lockout design, whether the API should refuse orders to pin-less legacy addresses, enforcing the CSP after a week of clean reports, and real provider accounts for map tiles, geocoding, Safepay live mode, SMS and e-mail. The store launch is a separate track: the product is a progressive web app with no native project, so it cannot be submitted to either store as it stands (Deliverable 8 gives the plan: a Capacitor shell, Sign in with Apple, background location for riders, about three to five weeks).

**Recommendation.** Soft-launch the web app (and the installable PWA) once the P0 checklist in Deliverable 9 is done, which is operational work of a few days. Do not announce a store launch date until the native shell exists and has been tested on devices; a Play listing through a Trusted Web Activity can come first if the business needs a store presence early.

### System architecture and data flow

```
 customer / kitchen / rider / admin browsers (PWA)
        │  HTTPS JSON (Bearer JWT, 1 h access + 30 d refresh)        │ WebSocket (Socket.IO, token at handshake)
        ▼                                                             ▼
 Next.js server (SSR shell, /api/geocode proxy, static)      Express API ──► Socket.IO rooms (user:*, role:*, order:*)
        │                                                             │   ▲
        │ rewrites /media /files /uploads ──────────────────────────► │   │ Redis adapter (multi-instance fan-out)
                                                                      ▼   │
                                   Prisma ──► PostgreSQL (orders, ledger, wallets, payouts, deliveries, audit_logs …)
                                   Redis  ──► rate-limit counters, BullMQ queues (email / push / SMS)
                                   S3 / local disk ──► public media (resized by sharp), private documents (signed links)
                                   Safepay ◄──► checkout redirect + signed webhook; Twilio; SMTP; Google tokeninfo
```

Key flows, as traced:

- **Order:** cart (server-side, one kitchen per order) → `POST /orders` with an idempotency key → server re-prices from DB prices, applies catalog deals and a promo code, computes the delivery fee per kitchen (kitchen-paid when a Nuray rider delivers), snapshots the delivery address, reserves stock with conditional updates in a fixed lock order, debits the wallet in the same transaction when paying by wallet → kitchen accepts → `Delivery` row created → dispatch picks a rider (community-based, batching) or the job stays in the pool → rider status machine (`assigned → arrived_at_pickup → picked_up → in_transit → arrived_at_customer → delivered`, each transition guarded by status, ownership and the customer's handover PIN) → ledger entries, commission, rider pay, COD cash custody.
- **Money:** every movement is a `ledger_entries` row; seller balance = platform-collected earnings − what the seller collected itself − payouts (pending included); rider balance from `rider_ledger_entries`; refunds lock the order row; payout requests lock the seller row.
- **Auth:** phone OTP or email+password (or Google) → JWT pair; `tokensValidAfter` ends every session (logout, suspension, role change, password reset, account closure); staff roles (`super_admin`/`admin`/`support`) enforced by a route-permission table on the API.
- **Realtime:** status changes and rider positions are emitted to the order room; membership is checked when joining and now revoked when a rider leaves or is suspended.

### Component responsibilities and dependencies

- `routes/*` wire middleware (authenticate, authorize, rate limits, validators, audit) → `controllers/*` (thin: auth guard, pass to service, shape the response) → `services/*` (all business rules; ownership checks are done here by querying with the caller's id) → Prisma.
- Cross-cutting: `middleware/audit.ts` (admin writes and refused attempts), `middleware/staff.ts` + `utils/permissions.ts` (staff roles), `utils/logger.ts` + `requestContext.ts` (request ids, redaction), `config/env.ts` (fail-closed production config), `storage/*` (public vs private files, signed links), `jobs/scheduler.ts` (advisory-locked periodic jobs).
- Frontend: `lib/api-client.ts` (token storage, transparent refresh), `lib/realtime/socket.ts` (one socket per tab, re-opens on token change), `lib/store/*` (auth and cart), page files are large (`app/page.tsx` 1,674 lines, product forms 1,600 lines) and mix fetching, state and layout.

### Architectural weaknesses (ranked) and recommended improvements

1. **Stateless JWT without rotation.** Logout now revokes everything (fixed), but refresh tokens are still not rotated or revocable one at a time and there is no per-device session list. Recommended before growth: a `refresh_tokens` table (jti, family, revokedAt) with rotation and reuse detection.
2. **Tokens in `localStorage`.** Any XSS exfiltrates a 30-day refresh token. Mitigations now in place: 1-hour access tokens, revocation on logout, CSP report-only + security headers, no `dangerouslySetInnerHTML` in the codebase. Recommended: move the refresh token to an httpOnly cookie on the API origin (needs CSRF handling) once the CSP is enforced.
3. **Large service and page files** (`order.service.ts` 1,836 lines; several 1,000+ line pages). Not a launch risk, but every money rule lives in `createOrder`; split pricing, promotions and delivery-fee computation into pure modules with unit tests (the `utils/*` pattern already used for ranking, dispatch and fees).
4. **Dev-server in-process scheduler.** Jobs run inside the API process. Fine at launch scale (advisory locks make several instances safe); move to a worker process when job load grows.
5. **Free map/geocoder tiers** (public OpenStreetMap tile and Nominatim servers) are for development only; configurable, but a provider account is needed before real traffic.
6. **No native mobile shell.** See Deliverable 8: the realistic path is a Capacitor wrapper around the deployed web app, not a rewrite.

## Deliverable 4: Security report

### What was verified

Every statement below was checked against the code on this branch and, where the local stack allowed it, exercised with real requests (the API checks in `backend/scripts/api-checks` against the running API, `verify-money-flows` on a fresh database, jest 375 tests).

**Sessions and identity**
- Phone OTP (Twilio), email + password (bcrypt, cost 10) or Google sign-in (token verified against Google's tokeninfo endpoint). Access tokens live 1 hour, refresh tokens 30 days; both carry a `typ` claim and are only accepted for their own purpose (an access token cannot mint tokens, a refresh token cannot call the API).
- One revocation clock per account (`tokensValidAfter`, millisecond precision). Logout, suspension, staff role change, password reset and account closure move it, which ends every token of every kind at once and cuts live Socket.IO connections. Changing the e-mail address needs the current password and leaves other sessions alone.
- Reset links go only to verified addresses. A new password is at least 8 characters (12 for staff), at most 200, not one of the ten thousand most common passwords (a bundled list, also matched with trailing digits or symbols stripped) and not built from the person's own name, phone number or e-mail name; the answer says which rule failed (`WEAK_PASSWORD` with a reason) and the web forms show it in English and Urdu. The rules apply when a password is chosen (sign-up, reset, staff creation and reset), never at sign-in.
- Login throttling counts failed attempts only, per address and account (10 per 15 minutes); a shared mobile-network address cannot be exhausted by successful sign-ins and one address cannot try many accounts. Codes and links are also capped per phone number and per e-mail address (hashed in the counter store), whoever asks, and a repeated reset request inside a minute does not send a second mail. The "confirm with your password" screens (closing the account, changing the e-mail address) accept five wrong passwords an hour per account, then answer 429; a wrong password there is a 400, because a 401 would make the web app refresh its session and retry. Signed-in API traffic is throttled per account, anonymous traffic per address.
- Staff accounts have a per-account lock after repeated failures (audit-logged). This protects the super admin from guessing but can be abused to lock that account out (see "Remaining risks").

**Authorization**
- Staff routes go through a route-to-permission table (`super_admin`, `admin`, `support`), tested in jest.
- Ownership is checked in the services by querying with the caller's id. Verified on: orders (customer, kitchen of an item, assigned rider), addresses, products and variants (cost prices only to the owning kitchen or staff), stock alerts, support tickets, payouts, documents.
- A rider gets the customer's name, phone, door details and pin only for a job it holds while the job is running; afterwards area and city only, no receipt, no bank-transfer details, no internal keys. The rider's live position reaches the customer and admins only, never the kitchen.
- Realtime rooms are joined only by the order's parties (checked on join) and left on hand-back, reassignment and suspension.

**Input handling**
- Every body is validated with zod schemas (free-text maxima, enums, coerced and bounded page/limit); repeated query keys are ignored; JSON bodies are limited to 1 MB; search terms are capped and their ILIKE wildcards escaped; malformed percent-encoding answers 400; CSV exports neutralise spreadsheet formulas; map pins must lie inside Pakistan; the category schema no longer passes unknown keys to Prisma; a kitchen's cover photo must be its own upload.
- Money inputs are never trusted: prices, fees, discounts and promo codes are recomputed server-side inside the order transaction, with row locks on promotions, orders and sellers where two requests could race (see Deliverable 7 for the ten money-flow defects that were fixed).

**Transport and browser hardening**
- API: `helmet`, CORS restricted to `CORS_ORIGIN` (required and https in production), gzip, `X-Powered-By` off, request ids, pino logs with redaction.
- Web app: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, a Content-Security-Policy in report-only mode (the only third-party origin left is Google sign-in; the web fonts and the Leaflet assets ship with the build, so no page or build calls Google Fonts), `X-Powered-By` off. HSTS is to be set at the TLS terminator (see the deployment guide).
- Tokens are kept in `localStorage`/`sessionStorage`. ## Deliverable 6: Rider navigation fix

### Root cause of the existing mapping issue

The flow existed but had seven gaps, all confirmed by reading the code and reproducing against the local stack:

1. **The order did not freeze the door.** `createOrder` snapshotted only the address lines, area, city and postal code (`backend/src/services/order.service.ts`, `deliveryAddressSnapshot`). The rider's "door details" (`houseNumber`, `landmark`, `addressLine2`) were read from the *live* saved address through the `order.deliveryAddress` relation (`rider.service.ts` `formatDelivery`). Editing the saved address after ordering changed what the rider saw; deleting it (the relation is `onDelete: SetNull`) made those details disappear. The delivery job's coordinates were copied from the live address at job creation, not from order time.
2. **Navigation used an undocumented Maps parameter.** The directions link carried `travelmode=two-wheeler`; the Google Maps URLs API documents only `driving`, `walking`, `bicycling` and `transit`, so the value was at best ignored.
3. **The Start button trusted the screen, not the server.** It was a plain link built from the last refresh: a job that had been cancelled, handed back or reassigned since could still open navigation, and a double tap opened two windows.
4. **No fallback without Google Maps** (iPhones without the Google Maps app; Android phones with another maps app).
5. **A rider kept the customer's door for good.** `GET /orders/:id` returned the live saved address, its pin and the receipt link to any rider whose job was on the order, also weeks after delivery (the rider endpoints already hid them once a job ended).
6. **A pin anywhere on earth was a deliverable address.** The address and kitchen validators only checked ±90/±180; a pin in Dubai with "DHA Karachi" typed as the area resolved to the DHA community and priced as a same-community delivery.
7. **Position sharing stopped while Google Maps was in front.** The dashboard's `watchPosition` had no handling for the page being hidden and shown again (browsers pause or drop the watch), so the customer's live map went stale for the whole ride, and three code paths that put a job back in the pool each cleared a different set of the previous rider's fields.

### Relevant code paths

- Order placement and the address snapshot: `backend/src/services/order.service.ts` (`createOrder`).
- Delivery job creation and the rider's view of a job: `backend/src/services/rider.service.ts` (`ensureDeliveryForOrder`, `formatDelivery`, `mapsUrl`, `updateDeliveryStatus`, `VALID_TRANSITIONS`).
- Rider screen: `frontend-web/app/riders/dashboard/page.tsx` (`navDestinationFor`, `navUrlFor`, `canStartNavigation`, `handleStartNavigation`, `handleAdvanceStatus`, `handleClaim`).
- Link builders (new): `frontend-web/lib/navigation-links.ts`.
- Address capture: `frontend-web/app/profile/addresses/page.tsx` (map pin required to save), `frontend-web/app/checkout/page.tsx` (an address without a pin cannot be used), `backend/src/validators/user-profile.validator.ts` (latitude −90..90, longitude −180..180, lengths).

### Implementation changes

A. **Customer selects a delivery location.** Saving an address requires a map pin (already enforced from the earlier work; coordinates validated server-side, and now required to be inside Pakistan for addresses and kitchens: `backend/src/utils/geo.ts`). At checkout, an address without a pin is flagged and cannot be ordered to. On `POST /orders` the server now snapshots **house number, landmark and the pin (latitude/longitude)** with the rest of the address, so the order carries the customer's intended location for good; the delivery job takes its coordinates from that snapshot, and the rider's door details read the snapshot first and fall back to the live address only for orders placed before this change.

B. **Rider receives an assigned job.** Unchanged server rule: the customer's name, phone and door details are only returned for the rider who holds the job while it is active (`reveal` in `formatDelivery`); `GET /orders/:id` now applies the same rule (area and city only once the job is delivered, failed or cancelled; no instructions, no receipt). The Start navigation button is rendered only for a job in `assigned`, `picked_up` or `in_transit`; it is disabled (grey, `aria-disabled`) when there is nothing to navigate to.

C. **Rider presses "Start navigation".**
1. The tap opens a blank window synchronously (browsers block pop-ups opened after a network call), then re-reads the rider's jobs from the server (`GET /riders/deliveries/mine`, which only ever returns this rider's jobs).
2. If the job is no longer there or no longer in a navigable state (cancelled, handed back, reassigned, finished), the window is closed, the rider is told, and the list refreshes.
3. Otherwise the destination is the saved pin when there is one, else the address text, and the window is pointed at `https://www.google.com/maps/dir/?api=1&destination=<lat>,<lng>` (no `travelmode`: the Maps app keeps the mode the rider last used, two-wheeler on a motorbike). This universal link opens the Google Maps app on Android and iOS when installed and the web map otherwise.
4. Fallback links next to the button: **Apple Maps** on iPhones (`https://maps.apple.com/?daddr=<lat>,<lng>&dirflg=d`, always installed) and **another maps app** on Android (`geo:<lat>,<lng>?q=<lat>,<lng>(label)`, which lets the phone choose).
5. If the pop-up was blocked, the page itself navigates to the maps link (the rider comes back with the back button). If the server cannot be reached, the link's own `href` still opens the last known destination.
6. A second tap while the first is being checked is ignored. Opening navigation changes nothing about the job: "arrived" and the handover PIN remain the rider's own taps. The saved address is never modified.

D. **Lifecycle.** Server-enforced transitions (`VALID_TRANSITIONS`): `assigned → arrived_at_pickup | picked_up`, `arrived_at_pickup → picked_up | in_transit | delivery_failed`, `picked_up → in_transit | delivery_failed`, `in_transit → arrived_at_customer | delivered | delivery_failed`, `arrived_at_customer → delivered | delivery_failed`. Every write is guarded on the status it was decided from (double taps and a cancel landing at the same time cannot apply a transition twice), ownership is re-checked inside the transaction, a cancelled or refunded order blocks every move, pickup needs the food to be ready and (for online orders) paid, and `delivered` needs the customer's PIN. New: a delivery cannot be reported failed while the kitchen is still cooking (`FOOD_NOT_READY`): a rider who cannot wait hands the job back, and the kitchen keeps the order. Hand-back, admin retry and rider suspension now reopen a job through one helper (`reopenDeliveryData`) that clears every trace of the previous rider (pay, bonus, arrival times, last position, pickup time) and adds that rider to the job's do-not-offer list; retry re-dispatches at once instead of waiting for the sweep. Going backwards is impossible. Opening navigation is not a state; "arrived at the kitchen/customer" and "delivered" are explicit rider actions.

E. **Live tracking.** Positions are sent only while the rider holds an active job, from the foreground page, at most every 3 s (server) and about every 10 s or 30 m of movement (client); the customer sees them only from pickup to arrival; a finished or released job stops sharing (and the rider is now removed from the order's realtime room when handing back or when suspended). Positions are now emitted to the customer and admins only, not to the order room the kitchen also sits in. When the rider comes back to the dashboard from Google Maps, the position watch is restarted and a fix is sent immediately, and the dashboard holds a screen wake lock while a job is running so the phone does not lock itself. True background tracking (dashboard closed or the phone in a pocket) is not possible from a web page; it needs the native wrapper in Deliverable 8.

### Remaining edge cases

## Deliverable 8: Google Play and App Store launch plan

### Where the product stands

- The repository holds a responsive Next.js web app with a PWA manifest, icons (192, 512, maskable), a service worker and web push. There is **no Android or iOS project** (no Capacitor, Expo, React Native, Flutter or native code). Nothing can be uploaded to either store today.
- Store prerequisites already in place: a public privacy policy (`/privacy`), terms and refund policy, an in-app account closure (`DELETE /users/me` from the profile page) and the public account-deletion page the stores link to (`/delete-account`), customer support e-mail in the legal pages, no demo login in production builds, HTTPS-only configuration, login with phone OTP, e-mail or Google.
- Features a store app must carry natively: push notifications (web push does not work inside an iOS WebView; Android works but FCM is expected), the rider's live location while riding (a web page stops reporting as soon as the phone locks or Maps is in front: see DELIV-7), opening Google Maps / Apple Maps from the app, the Safepay return redirect back into the app (deep link), camera access for kitchen and rider documents, and secure token storage.

### Recommended path: one Capacitor shell for both stores

1. **Week 1: foundation.** Add `@capacitor/core`, Android and iOS projects at the repository root (`mobile/`), pointing the WebView at the deployed web app (server URL mode) so one web build serves browsers and both apps; app id, icons, splash screens, status-bar and safe-area handling; `window.open` routed to the system browser / maps app (`@capacitor/app-launcher`, `comgooglemaps://` and `maps://` schemes with the https fallback already in `lib/navigation-links.ts`).
2. **Week 2: native capabilities.** `@capacitor/push-notifications` (FCM and APNs) registered through the existing `/push/subscriptions` API with a platform field; `@capacitor/geolocation` plus a background-location plugin for riders with the prominent in-app disclosure both stores require; `@capacitor/camera` for documents; `@capacitor/preferences` or secure storage for tokens (replace `localStorage`); universal links / app links for `/orders/:id`, the Safepay return URL and e-mailed reset links.
3. **Week 3: store requirements.** Sign in with Apple is mandatory on iOS because Google sign-in is offered (App Store guideline 4.8): add it to the API (`POST /auth/apple`, identity token verification) and the login page. Android target API level at the current Play requirement for new apps, 64-bit builds (an AAB), Play App Signing. Data-safety form (Play) and privacy "nutrition labels" (App Store): name, phone, e-mail, delivery address, precise location (customers at order time, riders while on duty), photos (documents), device/push identifiers; payments are handled by Safepay and cash, no card data is stored; data is not sold. Location permission strings and purpose texts in English and Urdu. Content rating questionnaire (no user-generated content beyond reviews and chat; declare both: reviews can be reported and hidden (NEW-ugc-1), the order chat has no report or block action yet).
4. **Week 4: review readiness and testing.** Reviewer test accounts (customer, kitchen, rider) on a staging stack with sample kitchens in a real community; a demo order path that does not need a real payment; screenshots and feature graphics per device class; English and Urdu store listings; crash-free sessions on at least two Android phones (one low-end) and two iPhones; the device checks from Deliverable 6 (Maps opens from the app, position keeps flowing while riding, PIN handover); accessibility pass (font scaling, VoiceOver / TalkBack on the main flows).
5. **Submission.** Play: internal testing track first, then closed testing with the 20-tester / 14-day requirement for new personal developer accounts if that applies to your account type, then production. App Store: TestFlight build to the team, then review; expect one round of questions on location use and account deletion.

**Faster alternative for Play only.** A Trusted Web Activity (Bubblewrap) wraps the deployed PWA in a day or two and is accepted on Google Play; it gives no background location and no APNs, so it is a stop-gap for presence, not the rider app. The App Store does not accept a thin web wrapper (guideline 4.2), so iOS needs the Capacitor path regardless.

### Pre-submission checklist

- [ ] Native shell builds for Android (AAB, 64-bit, target API at Play's current minimum) and iOS (Xcode, current SDK).
- [ ] Sign in with Apple implemented and tested; Google sign-in works inside the WebView (use the system browser flow, not an embedded one).
- [ ] Push notifications via FCM/APNs; web push kept for browsers.
- [ ] Rider background location with the prominent disclosure and the permission rationale; verified on a locked phone for a full ride.
- [ ] Deep links: order pages, Safepay return, e-mail links.
- [ ] Privacy policy, terms, refund policy and `/delete-account` URLs entered in both consoles; data-safety and privacy labels filled from the list above.
- [ ] Reviewer accounts and a reviewer note describing the demo order path.
- [ ] Store listings (en, ur), screenshots per device class, feature graphic, app icon without alpha (iOS).
- [ ] Crash reporting (Sentry already configured for the web app) wired to the native shells.
